# HTML 보고서 생성 계약 · v1.1.0

## 목적

GSR+ 분석 결과를 채팅의 긴 표가 아니라 브라우저에서 읽는 독립형 컨설팅 보고서로
전달한다. 분석과 디자인을 분리해, 내용이 바뀌어도 같은 표현 규칙을 유지한다.

이 스킬이 시장 조사나 판단을 수행하고, Python 렌더러는 **자료 검사·예산 합산·HTML
표현만** 수행한다. 렌더러에 사업계획서 PDF를 직접 넣으면 평가되는 프로그램이 아니다.

## 기본 산출물

`evaluate / report / portfolio / redesign / validate / update`는 HTML이 기본이다.
`context / init`은 기존 동작을 유지한다. 사용자가 `md`, `no-save`, “채팅으로만”이라고
하면 그 요청을 따른다. 기존 보고서·맥락은 덮어쓰지 않는다.

```text
.venture/reports/
  2026-09-21-140000-portfolio.html
  2026-09-21-140000-portfolio.json
```

지정 출력 경로가 있으면 우선한다. 파일 첨부 환경에서는 호스트가 허용하는 산출물
경로를 사용한다. 생성 파일에 접근할 수 있는 링크/경로만 제공한다. 브라우저 열기,
서비스 배포, 서버 실행, 외부 업로드는 보고서 생성에 필요하지 않다.

## 생성 순서

1. SKILL.md와 평가·근거 규칙에 따라 실제 자료를 먼저 읽는다.
2. `assets/report.template.json`의 빈 양식을 복사해 새 JSON을 작성한다.
   `assets/report.sample.json`은 **가상 샘플**이므로 점수·문장·예산을 실제 사업에 복사하지 않는다.
3. `assets/report.schema.json`에 맞춘다. 모든 텍스트는 일반 텍스트다. HTML·Markdown
   문법을 넣을 필요가 없다. 단락 안 줄바꿈은 `\n`으로 표시할 수 있다.
4. 실제 분석이면 `meta.status: "assessment"`, 샘플이면 `sample`, 미입력 양식이면 `template`이다.
   `meta.date`와 보고서 ID를 이번 평가에 맞게 정하고 데이터의 관측일은 출처별로 따로 적는다.
5. 검증 후 생성한다. 아래 변수는 호스트에서 확인한 실제 경로로 설정한다.

```bash
python3 "$SKILL_DIR/scripts/render_report.py" \
  --input "$DATA_FILE" --validate-only

python3 "$SKILL_DIR/scripts/render_report.py" \
  --input "$DATA_FILE" --output "$HTML_FILE"
```

`$SKILL_DIR`은 실제 로드한 스킬 폴더다. 개인·프로젝트·업로드 환경에 따라 다르므로
사용자의 홈 경로라고 무조건 가정하지 않는다. Python 3.9+, 표준 라이브러리만 사용한다.

## 데이터 구조

| 키 | 내용 |
|---|---|
| `schema_version` | `"1.1"` |
| `meta` | 제목, 부제, 날짜, ID, 수신자, 작성 주체, 등급 표시, 모드, 루브릭, 자료 범위, 외부 확인, 상태 |
| `summary` | 한 문장 결론, 설명, 권고별 제목·본문·근거, 지금/나중/하지 않을 일 |
| `ventures` | 사업별 현재 상태·신뢰도·근거·기호 판정·강점·위험·다음 행동·구조 변화 |
| `experiments` | 검증할 가설, 대상, 기간, 방법, 제안 성공/중단 기준, 비용 가정 |
| `roadmap` | 단계별 기간·과제·다음 단계 조건 |
| `budget` | 선택. 원화, 기간, 월/일회성 항목, 하한/상한, 세금·창업자 노동·제외 항목 |
| `uncertainties` | 결론을 바꿀 질문, 영향, 확인 방법 |
| `changes` | 선택. 이전 평가 대비 변경 내용·근거 |
| `sources` | `E1` 형식의 고유 ID, 상태, 제목, 페이지/줄/파일 위치, 날짜, 요약, 선택 URL |
| `limitations` | 자료·표본·법적 권리·검증 범위의 한계 |

`ventures[].ratings`의 기본 5개 항목은 `significant`, `scalable`, `sustainable`,
`frequency`, `network`다. 나머지 7개는 `retention`, `standardization`, `distribution`,
`demand`, `monetization`, `ai_defensibility`, `customization`이다. 미입력은 상세표에서
`?`로 표시하므로 자료가 없다는 사실을 근거 없는 부정 평가로 바꾸지 않는다.

```json
{
  "current": "△",
  "potential": "○",
  "reason": "현재는 고객별 수동 검수가 필요하다.",
  "condition": "공통 요청 유형을 표준화하고 건당 검수 시간이 감소하는지 관측한다.",
  "evidence": ["E1"]
}
```

`?` 외 기호에는 근거 ID가 필요하다. 바뀐 `potential`에는 구체적 `condition`이
필수다. 조건은 현재 실적이 아니다. 존재하지 않는 근거 ID, 중복 ID, 잘못된 기호,
날짜·음수 예산·범위 오류는 렌더러가 거부한다. 스키마가 유효하다고 판단까지
맞는 것은 아니므로 원자료와 대조한다.

## 출처와 개인정보

모든 근거는 `sources`에 넣고 문장 가까이 `evidence` 배열로 연결한다. 본문의 [E번호]는
보고서 안의 근거 원장으로 이동한다. 온라인 출처는 원문 URL과 확인 시점을 쓴다.
내부 문서는 제목·페이지/줄·시점을 적는다. `filecite`나 웹 도구의 전용 인용 토큰을
HTML에 그대로 쓰지 않는다. 전용 토큰은 로컬 HTML에서 작동하지 않는다.

관측 / 사용자진술 / 추론 / 가정 / 미확인 상태를 구분한다. 사업계획서 주장이나
이전 AI의 평가는 실제 로그를 관측한 것이 아니다. 원문 전체 대화, 고객 실명,
연락처, 계정 토큰·서명 URL, 비밀키는 포함하지 않는다. 기밀 표시가 암호화를
뜻하지 않는다. JSON도 보고서와 동일한 민감도로 취급한다.

## 예산

현재 렌더러는 KRW 정수 금액을 지원한다. 외화는 따로 설명하고 검증한 환율 또는
가정 환율·날짜를 밝혀 변환한 뒤 원화로 입력한다. 환율을 자동 조회하지 않는다.

`low`/`high`는 해당 항목의 일회 비용 또는 **1개월 비용**이다. `cadence`가 `monthly`면
`period_months`를 곱한다. 합계를 입력하지 말고 생성기가 계산하게 한다. 비율형
예비비는 분석 시 소계를 검산하고 금액으로 입력한다. 예비비 비율을 다시 자동 적용하지 않는다.

한쪽 범위라도 미정이면 해당 값에 `null`을 넣는다. 그런 항목은 전체 합계를 가장하지
않도록 `미산정`으로 표시하고, 알려진 완전한 항목만 `산정 항목 소계`에 포함한다.
미산정 비용을 0원으로 바꾸지 않는다. 창업자 노동·세금·채용·보증금·부품비 등
포함 범위는 반드시 설명한다.

## 디자인 계약

원본 CSS/JS는 `assets/report/`에 있다. 최종 파일에는 내부에 합쳐진다.
보고서를 볼 때 서버·Node·Python·AI 계정·인터넷이 필요하지 않다. 외부 원문 링크를
직접 누르면 해당 웹사이트가 열린다. AI 평가 과정은 호스트의 정책·연결 상태에 따른다.

- 흰색 배경, 진한 네이비 텍스트, 블루 소량, 넓은 여백, 얇은 회색 구분선.
- 표지에 수신자·기준일·검토 범위. 장마다 번호·한 문장 결론·Exhibit 표 제목.
- 비교표는 현재/조건부 전환. 기호 클릭 → 상세 근거. 12항목은 펼칠 수 있다.
- 고정 목차, 근거 원장 링크, 키보드 탐색, 모바일의 가로 스크롤 표.
- 인쇄 시 목차·버튼을 숨기고 상세 근거를 펼친다. 기본 A4 인쇄 스타일을 제공한다.
- 차트나 성공률·종합 점수를 장식으로 만들어 넣지 않는다. 기호를 숫자처럼 평균내지 않는다.
- KPMG/McKinsey의 로고·상표 배치·서체 파일·서명·실제 보고서 표지 복제는 하지 않는다.
  그 회사가 작성·검토한 보고서라고 표시하지 않는다. 독립 Venture Evaluator 디자인을 사용한다.

## 검수와 전달

가능한 환경에서 데스크톱·모바일 폭을 확인한다. 표가 잘리지 않는지, 근거 링크가
작동하는지, `?`와 조건부 기호가 구분되는지, 예산 소계와 반복 기간이 맞는지 확인한다.
파일 생성만 했다면 시각 검수를 했다고 하지 않는다. 브라우저 인쇄로 PDF를 만드는
경우 실제 페이지를 별도로 확인해야 하며, HTML 테스트를 PDF 품질 보증으로 표현하지 않는다.

최종 응답은 핵심 결론 몇 문장 + HTML 파일 + JSON 파일이다. HTML의 모든 문장을
채팅에 반복하지 않는다. 새 보고서를 만들었을 때만 링크를 준다.

## 실행 기능이 없는 환경

Python이 없지만 쓰기 도구가 있으면 스키마의 내용을 검토한 후 정적 HTML을 직접
만들 수 있다. 동적 기능이 빠지더라도 근거·한계·예산을 삭제하지 않는다. 가능하면
기본 CSS를 그대로 사용한다. 외부 JS 패키지를 도입하거나 웹서비스로 자료를 전송하지 않는다.
쓰기 자체가 불가능하면 Markdown으로 보고하고 HTML을 생성하지 못했다고 알린다.
